# v0.3.0

## 亮点

- 把前端契约固定到后端 jimu `v0.4.0`（`df33b82a740930cacaaa03676e76b99d699188ce`），并让 CI 用公开仓取证逐字节校验这个 pin，契约副本不再可能悄悄偏离来源提交。
- 补齐响应的两种形状偏差：新增 `unwrapPayload`（运行时仍是信封、契约只标载荷）与 `unwrapOk`（成功响应没有 `data` 键），后续注册页与租户管理页都建立在这两个出口上。

## 新增

- `scripts/sync-contract.sh`：契约同步入口。无参数时取本地 `../jimu` 的 `HEAD`（提交态，而非工作区），带 `<sha|tag|branch>` 时从公开远端 `fetch --depth=1` 取该提交，写入 `contracts/jimu.swagger.yaml` 与 `contracts/backend-commit.txt` 后自动运行 `pnpm run api:types`。

- `src/shared/api/unwrap.ts` 新增 `unwrapPayload<T>(body: unknown): T` 与 `unwrapOk(body: unknown): void`。
- `ErrorCode` 新增后续页面需要的取值：`forbidden = 1003`、`internal = 1005`、`conflict = 1009`、`userExists = 2002`。
- `docs/releases/v0.3.0.md`（本文件）。

## 修复

- 修正 `unwrap` 无法用于两类真实响应的缺陷：
  - 「载荷型」端点（`/auth/login`、`/auth/refresh`、`/auth/me`、`/auth/config`、`/auth/register`）契约只标了载荷，生成的响应类型不含信封字段；把载荷类型传给 `unwrap(body: Envelope | undefined)` 会触发 TS 弱类型报错（无属性重叠）。现在由 `unwrapPayload` 显式接纳 `unknown`，形状校验仍只有 `unwrap` 一份。
  - `response.OK(c, nil)` 的 `Body.Data` 是 `json:"data,omitempty"`，实测序列化为 `{"code":0,"message":"ok"}`——没有 `data` 键；`PUT /tenants/{id}`、`DELETE /tenants/{id}`、`PUT /tenants/{id}/plan` 都是这一类，用 `unwrap` 会把成功判成「响应缺少 data 字段」。现在由 `unwrapOk` 只确认 `code === 0`。
- 修正 `scripts/check_contract_pin.sh` 的 fail-open：`$sha` 后紧跟多字节字符（`——`）会被 macOS bash 3.2 并进变量名，触发 `set -u` 报 `unbound variable`，随后 `EXIT` trap 里成功的 `rm -rf` 又把异常退出码覆盖成 0——fetch 失败时脚本会「报绿」。改为 `${sha}` 花括号形式后，失败路径稳定退出 1。
- 修正跨任务的「非 2xx 业务码读不到」缺陷：`openapi-fetch` 只在 **2xx** 把解析后的响应体写进 `data`，非 2xx 写进 `error` 且 `data` 是 `undefined`；而后端业务错误全部使用非 2xx 状态（`1006`/`2006`/`2007` → 401，`1003`/`5005` → 403，`1001`/`4001`/`4002`/`5004` → 400，`2002`/`5003`/`5009` → 409，`1007` → 429）。只读 `data` 会把业务码统一退化成 `ApiError(-1, '服务端返回了空响应')`：登录页的错误码分支（TOTP / 图形验证码 / 限流）与注册页的 `4001`/`4002`/`2002` 分支（Task 1/3 的代码）静默失效，租户页的真实 `403`（`1003`）与 `409`（`5003`）也分辨不出来。`src/shared/api/unwrap.ts` 现在导出 `resolveEnvelope(result)`，按 `response.ok` 在 `data`/`error` 之间取信封，两侧的区分只此一处；`login`/`register`/`fetchAuthConfig` 与租户能力全部改用它（`register` 的 HTTP `429` 状态归一化保留，`logout`/`logoutAll` 的 2xx 路径不变）。该缺陷由 Task 4 的端到端运行暴露（真实 `403` 落到错误态而不是无权限态），此前的 mocked 单测只打桩 2xx（`auth-api.spec.ts` 用 HTTP `200` + 业务码），无法发现它。

## 说明

- **P1：雪花 ID 超出 JS 安全整数范围（本任务发现，未在本轮修复，属待用户决策项）**。跟踪方式：行内链路用例 `P1: create → assign plan → delete a runtime-created tenant` 目前由 **`test.fixme(true, 'P1: …')` 暂时跳过**——确定性跳过，不是 known-failure 标记（上一轮的 `test.fail` 会随被测 id 翻转，见上节 13 次实测），删掉该标记即重新启用整条链路。`GET /tenants` 把 `id` 作为 JSON number 输出（实测 `"id":370528943163310080`），`plan_id` 一样；契约里只声明 `type: integer`，没有 `format: int64`。该值远超 `Number.MAX_SAFE_INTEGER`（`9007199254740991`），JS 侧看到的是 `370528943163310100`（`JSON.parse('{"id":370528943163310080}').id` 与 `String(Number('370528943163310080'))` 一致），与真值差 20。`TenantsView` 的「编辑」「分配套餐」「删除」都用 `row.id` 拼路径参数，因此这些行内动作会打到错误的租户 ID。
  **对同一个舍入后的 ID，后端三种行为（实测，admin token，`BASE=/api/v1`）**：`GET /tenants/370528943163310100` → **`404` + `{"code":5001,"message":"租户不存在"}`**；`DELETE /tenants/370528943163310100` → **`404` + `5001`**；`PUT /tenants/370528943163310100/plan` → **`200` + `{"code":0,"message":"ok"}`**（对 `999999999` 同样返回 `code:0`）。**静默假成功是三者中最危险的一个**：前端收不到任何错误信号，用户看到写入成功，刷新后租户仍是「未分配」。
  **精确机制**：本轮实测的雪花 ID 都是 2^22 的倍数，`JSON.parse` 存下的 double 对这些值仍然精确，错位发生在把数字序列化回 URL 路径时——JS 给出的是「最短可往返小数」，可以不是整数本身（`370528943163310080` → `370528943163310100`）。是否命中取决于后端当次生成的 ID，实测 13 次真机运行 12 次命中，见上节。
  **推荐修复**：后端把 `id` / `plan_id` 序列化为 string，或在契约里标 `format: int64` 并让生成类型按 string 处理；前端随后另需一次契约同步（`pnpm run api:types`）。后端另需修 `PUT /tenants/{id}/plan` 对不存在的租户返回 `code:0` 的缺陷。以上修复**未在本轮实施**，属待用户决策项。
- 公开注册出来的用户是**零角色**：`GET /auth/me` 返回 `200` + 两个空数组，但 `GET /tenants` 是 `403`（`1003`）。界面把 `403` 渲染成无权限页并留在路由内，这不是会话失效——只有 `401` 才刷新凭证或回登录页，两者不混用。
- `GET /tenants` 不筛选状态时必须**完全省略** `status`：显式写成 `?status=` 会被 gin 按整数绑成 `0`，只查停用（实测 `total:0`）。`status=0` 是合法筛选值，必须保留。
- 本期最终交付：契约 pin 与 pin 校验、响应形状适配（`unwrapPayload`/`unwrapOk`/`unwrapEnvelope`）、会话引导（`/auth/me`）与 `permissions` 判权、运行时开关的注册页、权限驱动的租户管理页，以及 `E2E_REAL_BACKEND=1` 门控的真机用例。
- 契约 pin 只能指向**已推送**的提交：CI 用公开仓 `fetch` 取证，本地未推送的提交会让 `API Contract` 变红。这是有意为之，不是缺陷。
- `unwrap` 的签名与行为未变，既有 5 条用例保持不动。
- 契约中的 `/api/v1/admin/error-codes` 与 `/api/v1/admin/ratelimit/auth` 地址已修正，但 console 能力还没有接上认证链，运行时仍返回 401；前端不消费这两个端点。
- 后端 `/auth/logout`、`/auth/logout-all` 返回 `gin.H{}`，`data` 是 `{}` 而非缺失，因此仍由 `unwrap` 处理。
- `vitest.config.ts` 的 `test.server.deps.inline` 内联了 `element-plus`：不内联时它经 Node 的 ESM/CJS 互操作把 `async-validator` 解析成 `{ default }` 而非构造函数，`el-form` 的校验在 jsdom 下静默 `resolve(true)`；内联后注册页的必填断言才真正由 `el-form` 的 `FormRules` 驱动，即「不填 `tenant_name` 不发请求」是有效断言而非空跑。

## 会话引导与权限判定

### 新增

- `src/shared/auth/identity.ts`：`ensureIdentity(): Promise<IdentityStatus>`。受保护导航前加载 `GET /auth/me`；并发调用共享同一请求（单飞），只在成功时缓存，失败后下一次导航会重试。401/404 清空身份并返回 `'unauthenticated'`，500 与网络错误返回 `'unavailable'`（会话与身份都不动）。该函数自身不导航、不清 token。

## 注册页（运行时开关）

### 新增

- `src/features/auth/api.ts` 追加 `RegisterPayload`、`fetchAuthConfig()`、`register()`：`fetchAuthConfig` 走公开端点 `GET /auth/config`；`register` 走 `POST /auth/register`，先把 HTTP `429` 归一化为 `ErrorCode.rateLimited`（限流响应体可能不是标准信封），再交给 `unwrapPayload<RegisterResult>` 解包。
- `src/features/auth/views/RegisterView.vue`：注册页。`onMounted` 读开关，`public_registration=false` 时只渲染 `data-test="register-closed"`（「注册未开放」+ 返回登录），不渲染表单也不发请求；开关读取失败时保持关闭态（「无法确认注册开关，请稍后重试」+ 重试）。`provisioning_enabled=true` 才渲染 `tenant_name`（必填）与 `tenant_code`（可选），载荷按开关最小化构造，不发送多余的租户字段。
- 路由 `/register`（`name: 'register'`，`meta: { public: true }`）。
- `tests/unit/register-view.spec.ts`：7 条用例，覆盖关闭态、开关读取失败、普通注册载荷、开通式注册必填与可选字段、验证码揭示、用户名占用、限流。

### 变更

- `src/features/auth/views/LoginView.vue`：`onMounted` 读同一开关，只有 `public_registration === true` 才显示 `data-test="register-link"` 的「注册新账号」入口（关闭或读取失败都不显示）；`?registered=1` 时顶部显示 `el-alert type="success"`「注册成功，请使用新账号登录」。
- `tests/unit/login-view.spec.ts`：api mock 工厂补上 `fetchAuthConfig`——`LoginView` 挂载时就会调用它，缺了会让既有用例全红；`beforeEach` 给出默认关闭值，并新增「关闭态不显示注册入口」与「开放态显示入口与成功提示」两条用例。

### 验证

- `pnpm run check` 通过（`api:check`、`fmt:check`、`lint`、`typecheck`、`test`、`build`），单测 102 条全绿。
- `pnpm run test:e2e` 通过（6 条）。
- TDD 顺序：`tests/unit/register-view.spec.ts` 先失败在 `Failed to resolve import ".../features/auth/views/RegisterView.vue"`，实现后 7 条全绿。`tests/unit/login-view.spec.ts` 的两条新用例里，「开放态显示注册入口与成功提示」在改 `LoginView.vue` 前失败（`register-link` 不存在、没有「注册成功」文案）；「关闭态不显示注册入口」在实现前即通过——默认状态就是没有入口，属 fail-closed 的既有行为，不作为 RED 证据。

### 说明

- 注册不签发 token：`POST /auth/register` 只返回 `{user, tenant?}`（普通注册只有 `user`），前端一律跳 `/login?registered=1`。
- 请求体只包含显式注册字段；`tenant_name`/`tenant_code` 仅在开通式注册下出现，不发送任何推导或缓存的租户标识。
- `el-form` 的规则校验依赖 `async-validator`；jsdom 下该校验曾整体静默失效，成因与根治（`vitest.config.ts` 内联 `element-plus`）见上文「说明」。字段规则的唯一来源是 `FormRules`，`validateForm` 不再保留任何组件侧必填兜底。

## 租户管理页（权限驱动）

### 新增

- `src/features/tenants/params.ts`：`TenantFilters` / `TenantListQuery` / `buildTenantListQuery`。「不筛选状态」时**完全不传** `status`——显式写成 `?status=` 会被 gin 按整数绑成 `0`（只查停用）；`status: 0` 是合法筛选值，必须保留。`keyword` 去空白后**传原文**（后端已对 `%`/`_`/`!` 转义），空串省略。
- `src/features/tenants/api.ts`：`listTenants` / `listPlans` / `createTenant` / `updateTenant` / `deleteTenant` / `assignTenantPlan`。列表与套餐走 `unwrapEnvelope` 以保留 `total`/`page`/`page_size`；三个写操作走 `unwrapOk`（成功响应没有 `data` 键）。`Tenant.id` 只作路径参数，`plan_id: 0` 原样发出（取消套餐）。
- `src/features/tenants/plan-name.ts`：`resolvePlanName`——`plan_id === 0` → 「未分配」；套餐列表未命中 → `#<id>`。
- `src/features/tenants/views/TenantsView.vue`：筛选（关键字 / 状态 / 排序字段 / 方向）、表格、分页与新建、编辑、删除、分配套餐对话框。四态互斥且按序判定：无权限 → 加载中 → 错误 → 空 → 表格；`403`/`1003` 留在本路由渲染说明、不跳登录，本地缺 `GET` 权限时**不发列表请求**。行内「编辑」「删除」「分配套餐」按**各自请求路径**判权：`apiResource(`/tenants/${id}`)` 的 `PUT`/`DELETE` 与 `apiResource(`/tenants/${id}/plan`)` 的 `PUT`；套餐列表只由 `apiResource('/tenant-plans')` 的 `GET` 决定是否请求（缺该权限时 `enabled: false`，不请求）。表格包在横向滚动容器内。
- `src/app/query.ts`：`queryClient`（`retry: false`、`staleTime: 30s`、`refetchOnWindowFocus: false`）。
- 路由 `/platform/tenants`（`name: 'platform-tenants'`），**不加权限守卫**：无权限用户必须能进入并看到无权限页，而不是被重定向。
- `tests/unit/tenant-params.spec.ts`（6 条）、`tenant-plan-name.spec.ts`（3 条）、`tenants-api.spec.ts`（10 条）、`tenants-view.spec.ts`（8 条）、`e2e/tenants.spec.ts`（3 条）。

### 变更

- `src/shared/api/unwrap.ts`：`Envelope` 增加 `total`/`page`/`page_size`，新增 `unwrapEnvelope`（校验信封并原样返回，分页端点不再丢元数据）；`unwrap`/`unwrapOk` 里重复的三段校验抽成同一个 `assertOk`。`unwrap` 的签名与可观察行为未变。
- `src/main.ts`：注册 `VueQueryPlugin`（置于 `ElementPlus` 之后、`router` 之前），并接入 `src/app/query.ts` 的 `queryClient`。
- `src/layouts/PortalLayout.vue`、`src/views/PortalView.vue`：导航项「租户管理」与工作区入口「管理租户」按 `hasPermission(apiResource('/tenants'), 'GET')` 渲染；平台工作区 lead 文案改为已接入真实后端。
- `playwright.config.ts`：`use.testIdAttribute: 'data-test'`——仓库里的组件钩子统一是 `data-test`，默认的 `data-testid` 会让 `getByTestId` 找不到元素。
- `e2e/helpers/session.ts`：新增 `ZERO_ROLE_IDENTITY`（`/auth/me` 返回 `200` + 空数组，是合法身份而不是会话失效）。

### 修复

- 行内「分配套餐」曾按套餐列表的 `GET` 权限渲染：持 `GET /api/v1/tenant-plans` 而无 `/api/v1/tenants/*` 的 `PUT` 时会看到按钮、保存必然 `403`；反之有 `PUT` 而无套餐列表 `GET` 时按钮整个消失。现按动作自己的请求路径 `apiResource(`/tenants/${id}/plan`)` + `PUT` 逐行判权（与「编辑」「删除」同一写法），套餐列表 `GET` 只保留给 `listPlans` 的 `enabled`。
- 非 2xx 的业务码读不到：openapi-fetch 只在 **2xx** 把响应体写进 `data`，非 2xx（`403`、`409`）写进 `error`。只读 `data` 时，`GET /tenants` 的真实 `403`（`{code:1003,...}`）与 `DELETE /tenants/{id}` 的真实 `409`（`{code:5003,...}`）都会退化成「服务端返回了空响应」（`unknown`）——页面把无权限渲染成错误态，后端「默认租户不可删除」的文案与 `request_id` 全部丢失。修复见上文顶层「修复」的 `resolveEnvelope`（该 helper 最终落在 `src/shared/api/unwrap.ts`，登录/注册同批修复），业务码判断仍然只有 `unwrap`/`unwrapEnvelope`/`unwrapOk` 一处。

### 说明

- 前端不判断默认租户：没有任何 `id === 1` / `code === 'default'` 的特判，「删除」照常发出，`5003` 的后端文案与 `request_id` 由 `ElMessage.error` 呈现。

- 空状态的「新建租户」主操作与工具栏按钮一样按 `hasPermission(apiResource('/tenants'), 'POST')` 渲染：缺 `POST` 权限时只渲染一句空状态说明，不再给出注定 `403` 的动作。两个位置复用同一个 `data-test="tenant-create"` 钩子。是否真能创建仍由后端判定（`1003` 在对话框内呈现），前端不预判。
- 三处与简报原文的必要偏差（原样照抄必然失败，真实输出见 `task-4-report.md`）：`tenants-api.spec.ts` 的 `ApiError` 导入在 lint 下未被使用（改为断言 `rejects.toBeInstanceOf(ApiError)`，原断言不削弱）；`e2e/tenants.spec.ts` 的 `getByRole('table')` 撞上 el-table 的 header/body 双 `<table>` strict mode（改用 `getByTestId('tenants-table')`）；第三个 e2e 用例没有打桩 `/tenant-plans`，会落到本机后端并因假 refresh token 触发 `401` → 刷新失败 → 会话失效跳登录（补上打桩后用例自洽）。
