# v0.3.0

## 亮点

- 把前端契约固定到后端 jimu `v0.4.0`（`df33b82a740930cacaaa03676e76b99d699188ce`），并让 CI 用公开仓取证逐字节校验这个 pin，契约副本不再可能悄悄偏离来源提交。
- 补齐响应的两种形状偏差：新增 `unwrapPayload`（运行时仍是信封、契约只标载荷）与 `unwrapOk`（成功响应没有 `data` 键），后续注册页与租户管理页都建立在这两个出口上。

## 新增

- `scripts/sync-contract.sh`：契约同步入口。无参数时取本地 `../jimu` 的 `HEAD`（提交态，而非工作区），带 `<sha|tag|branch>` 时从公开远端 `fetch --depth=1` 取该提交，写入 `contracts/jimu.swagger.yaml` 与 `contracts/backend-commit.txt` 后自动运行 `pnpm run api:types`。
- `scripts/check_contract_pin.sh`：契约 pin 校验。读 `contracts/backend-commit.txt`，从公开仓 `fetch --depth=1` 取该 SHA，再逐字节比对 `docs/openapi/swagger.yaml`；只读、零凭据、fail-closed——pin 一个未推送的提交会直接 fetch 失败。
- `src/shared/api/unwrap.ts` 新增 `unwrapPayload<T>(body: unknown): T` 与 `unwrapOk(body: unknown): void`。
- `ErrorCode` 新增后续页面需要的取值：`forbidden = 1003`、`internal = 1005`、`conflict = 1009`、`userExists = 2002`。
- `docs/releases/v0.3.0.md`（本文件）。

## 变更

- 契约 pin 由 `3dea4ab780c1d5ad3d3fe11860946ea4b2e44aa0` 换为 `df33b82a740930cacaaa03676e76b99d699188ce`；`contracts/jimu.swagger.yaml`（2437 行）、`contracts/jimu.openapi.yaml` 与 `src/shared/api/generated.ts` 随之重新生成。
- 契约变化带来的类型落地：`/auth/me` → `application.MeView`、`/auth/config` → `interfaces.AuthConfigResponse`、`/auth/register` → `application.RegisterResponse`、`/auth/login` 与 `/auth/refresh` → `contract.TokenPair`，五个端点均为「载荷型」标注；`/tenants` GET → `application.TenantPageResponse`、`POST /tenants` 与 `GET /tenants/{id}` → `application.TenantBodyResponse`、`/tenant-plans` → `application.PlanPageResponse`，四个端点已带信封字段；`src/features/auth/api.ts` 的 `login()` 解包入口改为 `unwrapPayload<TokenPair>`。
- CI 的 `API Contract` job 在 `pnpm run api:check` 之后新增一步 `bash scripts/check_contract_pin.sh`；不新增 job，聚合门禁 `CI Gate` 的 `needs` 与 `scripts/check_ci_gate.sh` 的清单不变。
- `package.json` 版本 `0.2.0` → `0.3.0`。
- 契约中 `/api/v1/admin/*` 的重复 `basePath` 前缀已由后端修正，`/admin/error-codes`、`/admin/ratelimit/auth` 的生成路径不再是 `/api/v1/api/v1/...`。

## 修复

- 修正 `unwrap` 无法用于两类真实响应的缺陷：
  - 「载荷型」端点（`/auth/login`、`/auth/refresh`、`/auth/me`、`/auth/config`、`/auth/register`）契约只标了载荷，生成的响应类型不含信封字段；把载荷类型传给 `unwrap(body: Envelope | undefined)` 会触发 TS 弱类型报错（无属性重叠）。现在由 `unwrapPayload` 显式接纳 `unknown`，形状校验仍只有 `unwrap` 一份。
  - `response.OK(c, nil)` 的 `Body.Data` 是 `json:"data,omitempty"`，实测序列化为 `{"code":0,"message":"ok"}`——没有 `data` 键；`PUT /tenants/{id}`、`DELETE /tenants/{id}`、`PUT /tenants/{id}/plan` 都是这一类，用 `unwrap` 会把成功判成「响应缺少 data 字段」。现在由 `unwrapOk` 只确认 `code === 0`。
- 修正 `scripts/check_contract_pin.sh` 的 fail-open：`$sha` 后紧跟多字节字符（`——`）会被 macOS bash 3.2 并进变量名，触发 `set -u` 报 `unbound variable`，随后 `EXIT` trap 里成功的 `rm -rf` 又把异常退出码覆盖成 0——fetch 失败时脚本会「报绿」。改为 `${sha}` 花括号形式后，失败路径稳定退出 1。

## 验证

- `pnpm run check` 通过（`api:check`、`fmt:check`、`lint`、`typecheck`、`test`、`build`）。
- 新增 6 条单测先失败（`unwrapPayload is not a function` / `unwrapOk is not a function`）后通过，`tests/unit/api-unwrap.spec.ts` 共 11 条全绿。
- pin 校验写入前后各跑一次：同步前 `bash scripts/check_contract_pin.sh`（旧 pin `3dea4ab`）通过、`bash scripts/check_contract_pin.sh df33b82a…` 失败并输出真实逐行差异；同步后无参数运行通过。
- 同步结果逐字节核对：`contracts/jimu.swagger.yaml` 的 sha256 为 `331e2540fd00b2e9325e0b9b2d1f4023a5512cbcacb5e1c33c9b6d29bdf9298b`，2437 行，与 `df33b82a…` 的 `docs/openapi/swagger.yaml` 一致。
- `grep -c 'application.MeView\|interfaces.AuthConfigResponse\|application.RegisterResponse\|application.TenantPageResponse\|application.TenantBodyResponse\|application.PlanPageResponse' src/shared/api/generated.ts` 输出 13，确认生成的是真实字段类型而非 `unknown`。
- 反向钉住：把 `login()` 退回 `unwrap<TokenPair>(data)` 会报 `error TS2345 … has no properties in common with type 'Envelope'`，证明 `unwrapPayload` 不是冗余抽象。

## 说明

- 契约 pin 只能指向**已推送**的提交：CI 用公开仓 `fetch` 取证，本地未推送的提交会让 `API Contract` 变红。这是有意为之，不是缺陷。
- `unwrap` 的签名与行为未变，既有 5 条用例保持不动。
- 契约中的 `/api/v1/admin/error-codes` 与 `/api/v1/admin/ratelimit/auth` 地址已修正，但 console 能力还没有接上认证链，运行时仍返回 401；前端不消费这两个端点。
- 本期只交付契约 pin、pin 校验与响应形状适配；会话引导（`/auth/me`）、注册页与租户管理页由后续任务交付。
- 后端 `/auth/logout`、`/auth/logout-all` 返回 `gin.H{}`，`data` 是 `{}` 而非缺失，因此仍由 `unwrap` 处理。
