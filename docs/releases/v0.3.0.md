# v0.3.0

## 亮点

- 把前端契约固定到后端 jimu `v0.4.0`（`df33b82a740930cacaaa03676e76b99d699188ce`），并让 CI 用公开仓取证逐字节校验这个 pin，契约副本不再可能悄悄偏离来源提交。
- 补齐响应的两种形状偏差：新增 `unwrapPayload`（运行时仍是信封、契约只标载荷）与 `unwrapOk`（成功响应没有 `data` 键），后续注册页与租户管理页都建立在这两个出口上。

## 新增

- `scripts/sync-contract.sh`：契约同步入口。无参数时取本地 `../jimu` 的 `HEAD`（提交态，而非工作区），带 `<sha|tag|branch>` 时从公开远端 `fetch --depth=1` 取该提交，写入 `contracts/jimu.swagger.yaml` 与 `contracts/backend-commit.txt` 后自动运行 `pnpm run api:types`。
- `scripts/check_contract_pin.sh`：契约 pin 校验。读 `contracts/backend-commit.txt`，从公开仓 `fetch --depth=1` 取该 SHA，再逐字节比对 `docs/openapi/swagger.yaml`；只读、零凭据、fail-closed——pin 一个未推送的提交会直接 fetch 失败。
- `src/shared/api/unwrap.ts` 新增 `unwrapPayload<T>(body: unknown): T` 与 `unwrapOk(body: unknown): void`。
- `ErrorCode` 新增后续页面需要的取值：`forbidden = 1003`、`internal = 1005`、`conflict = 1009`、`userExists = 2002`。
- `docs/releases/v0.3.0.md`（本文件）。

## 修复

- 修正 `unwrap` 无法用于两类真实响应的缺陷：
  - 「载荷型」端点（`/auth/login`、`/auth/refresh`、`/auth/me`、`/auth/config`、`/auth/register`）契约只标了载荷，生成的响应类型不含信封字段；把载荷类型传给 `unwrap(body: Envelope | undefined)` 会触发 TS 弱类型报错（无属性重叠）。现在由 `unwrapPayload` 显式接纳 `unknown`，形状校验仍只有 `unwrap` 一份。
  - `response.OK(c, nil)` 的 `Body.Data` 是 `json:"data,omitempty"`，实测序列化为 `{"code":0,"message":"ok"}`——没有 `data` 键；`PUT /tenants/{id}`、`DELETE /tenants/{id}`、`PUT /tenants/{id}/plan` 都是这一类，用 `unwrap` 会把成功判成「响应缺少 data 字段」。现在由 `unwrapOk` 只确认 `code === 0`。
- 修正 `scripts/check_contract_pin.sh` 的 fail-open：`$sha` 后紧跟多字节字符（`——`）会被 macOS bash 3.2 并进变量名，触发 `set -u` 报 `unbound variable`，随后 `EXIT` trap 里成功的 `rm -rf` 又把异常退出码覆盖成 0——fetch 失败时脚本会「报绿」。改为 `${sha}` 花括号形式后，失败路径稳定退出 1。
- 修正跨任务的「非 2xx 业务码读不到」缺陷：`openapi-fetch` 只在 **2xx** 把解析后的响应体写进 `data`，非 2xx 写进 `error` 且 `data` 是 `undefined`；而后端业务错误全部使用非 2xx 状态（`1006`/`2006`/`2007` → 401，`1003`/`5005` → 403，`1001`/`4001`/`4002`/`5004` → 400，`2002`/`5003`/`5009` → 409，`1007` → 429）。只读 `data` 会把业务码统一退化成 `ApiError(-1, '服务端返回了空响应')`：登录页的错误码分支（TOTP / 图形验证码 / 限流）与注册页的 `4001`/`4002`/`2002` 分支（Task 1/3 的代码）静默失效，租户页的真实 `403`（`1003`）与 `409`（`5003`）也分辨不出来。`src/shared/api/unwrap.ts` 现在导出 `resolveEnvelope(result)`，按 `response.ok` 在 `data`/`error` 之间取信封，两侧的区分只此一处；`login`/`register`/`fetchAuthConfig` 与租户能力全部改用它（`register` 的 HTTP `429` 状态归一化保留，`logout`/`logoutAll` 的 2xx 路径不变）。该缺陷由 Task 4 的端到端运行暴露（真实 `403` 落到错误态而不是无权限态），此前的 mocked 单测只打桩 2xx（`auth-api.spec.ts` 用 HTTP `200` + 业务码），无法发现它。
- 修正租户页的分页与筛选没有随结果集收敛的缺陷：状态/排序字段/排序方向变化不重置页码，删掉最后一页的最后一行后仍用越界页码请求，页面会把「本页为空」渲染成「还没有租户」；且分页只在表格分支渲染，空/错误态没有离开的入口。`src/features/tenants/params.ts` 新增纯函数 `clampPage(page, pageSize, total)`（`total <= 0` → 1，其余收敛到 `[1, ceil(total / pageSize)]`）；三个筛选/排序下拉的 `change` 统一调用 `resetPage()`；结果回来是空数组且 `total > 0` 时用 `clampPage` 把 `filters.page` 收敛到最后一页并重新查询；`el-pagination` 改为只要 `total > 0` 就渲染，不再被状态分支藏起来。
- 修正 P1 的「静默假成功」：雪花 ID 超出 JS 安全整数范围时，行内「编辑 / 删除 / 分配套餐」改为**禁用**并带 `title`/`aria-label` 说明，同时页面顶部渲染一条不可关闭的 `el-alert` 说明原因——写操作不再可能落到被改写的 ID 上，也不会再出现 `PUT /tenants/{id}/plan` 收到 `code:0` 的假成功。判定用 `isPreciseId(id) = Number.isSafeInteger(id)`，**不做 BigInt 补偿**，也不改变 ID 的序列化方式；后端改为字符串序列化后该守卫随类型一起失效。
- 修正「身份不可用被渲染成没有权限」：`/auth/me` 返回 500、网络错误或业务码不是 `2001` 的 404 时身份为 `null`、`hasPermission` 必然 false，租户页此前直接渲染「没有访问租户管理的权限」，把一次后端抖动伪装成权限被收回且没有重试入口。`src/shared/auth/identity.ts` 现在把每次加载结果写进可响应的 `getIdentityStatus()`（`'ok' | 'unauthenticated' | 'unavailable' | 'unknown'`，`clearIdentity()`/`clearSession()` 重置为 `'unknown'`）；租户页在无权限且状态为 `'unavailable'` 时渲染独立的 `data-test="tenants-identity-error"` 状态与重试按钮（重新调用 `ensureIdentity()`），只有身份为 `'ok'` 且仍缺 `GET /api/v1/tenants`、或列表本身回 `1003` 时才渲染 `tenants-forbidden`。
- 修正「`/auth/me` 的任一 404 都等于会话失效」：404 也会由代理重写、basePath 错配、后端回滚产生，按会话失效处理会让用户每次导航都被登出（登录循环）。`ErrorCode` 新增 `userNotFound = 2001`；`loadIdentity()` 对非 2xx 用 `resolveEnvelope({ data, error, response })` 读取业务码：`401` → `'unauthenticated'`；`404` 且 `code === 2001` → `'unauthenticated'`；其余 404/非 2xx → `'unavailable'` 且保留会话。
- 修正 `scripts/sync-contract.sh` 的写入方式：先写临时文件、校验 `^swagger:` 通过后再 `mv` 到 `contracts/jimu.swagger.yaml`，失败时不会把已跟踪的契约截断；`scripts/check_contract_pin.sh` 导出 `GIT_TERMINAL_PROMPT=0`，凭据缺失时直接失败而不是等待交互输入。

## 说明

- **P1：雪花 ID 超出 JS 安全整数范围（本任务发现，根因在后端序列化，属待用户决策项）**。跟踪方式：行内链路用例 `P1: create → assign plan → delete a runtime-created tenant` 目前由 **`test.fixme(true, 'P1: …')` 暂时跳过**——确定性跳过，不是 known-failure 标记（上一轮的 `test.fail` 会随被测 id 翻转，见上节 13 次实测）；前端已对不可精确的 ID 禁用行内写操作（见上节「修复」），所以只有在后端把 ID 序列化为字符串、前端收掉守卫之后删掉该标记，整条链路才可重新启用。`GET /tenants` 把 `id` 作为 JSON number 输出（实测 `"id":370528943163310080`），`plan_id` 一样；契约里只声明 `type: integer`，没有 `format: int64`。该值远超 `Number.MAX_SAFE_INTEGER`（`9007199254740991`），JS 侧看到的是 `370528943163310100`（`JSON.parse('{"id":370528943163310080}').id` 与 `String(Number('370528943163310080'))` 一致），与真值差 20。`TenantsView` 的「编辑」「分配套餐」「删除」都用 `row.id` 拼路径参数，因此这些行内动作会打到错误的租户 ID。
  **对同一个舍入后的 ID，后端三种行为（实测，admin token，`BASE=/api/v1`）**：`GET /tenants/370528943163310100` → **`404` + `{"code":5001,"message":"租户不存在"}`**；`DELETE /tenants/370528943163310100` → **`404` + `5001`**；`PUT /tenants/370528943163310100/plan` → **`200` + `{"code":0,"message":"ok"}`**（对 `999999999` 同样返回 `code:0`）。**静默假成功是三者中最危险的一个**：前端收不到任何错误信号，用户看到写入成功，刷新后租户仍是「未分配」。
  **精确机制**：本轮实测的雪花 ID 都是 2^22 的倍数，`JSON.parse` 存下的 double 对这些值仍然精确，错位发生在把数字序列化回 URL 路径时——JS 给出的是「最短可往返小数」，可以不是整数本身（`370528943163310080` → `370528943163310100`）。是否命中取决于后端当次生成的 ID，实测 13 次真机运行 12 次命中，见上节。
  **推荐修复**：后端把 `id` / `plan_id` 序列化为 string，或在契约里标 `format: int64` 并让生成类型按 string 处理。后端另需修 `PUT /tenants/{id}/plan` 对不存在的租户返回 `code:0` 的缺陷。
  **完成判据（P1 收口，按顺序执行）**：后端把 `id` / `plan_id` 序列化为 JSON string → 同步契约（`scripts/sync-contract.sh <ref>` 更新 pin 与契约副本）→ `pnpm run api:types` 重新生成类型 → 按新类型收掉 `isPreciseId` 守卫（字符串 ID 不再是数字，行内按钮恢复可用）→ 删掉 `e2e/real-backend.spec.ts` 的 `test.fixme` 并重新启用整条链路，届时断言应真正通过。前端本轮已给不可精确的 ID 加上「禁用行内写操作 + 页面级提示」的诚实守卫，不会再产生静默假成功；P1 的根因仍在后端序列化，故用例仍确定性跳过。
- 公开注册出来的用户是**零角色**：`GET /auth/me` 返回 `200` + 两个空数组，但 `GET /tenants` 是 `403`（`1003`）。界面把 `403` 渲染成无权限页并留在路由内，这不是会话失效——只有 `401` 才刷新凭证或回登录页，两者不混用。
- `GET /tenants` 不筛选状态时必须**完全省略** `status`：显式写成 `?status=` 会被 gin 按整数绑成 `0`，只查停用（实测 `total:0`）。`status=0` 是合法筛选值，必须保留。
- 本期最终交付：契约 pin 与 pin 校验、响应形状适配（`unwrapPayload`/`unwrapOk`/`unwrapEnvelope`）、会话引导（`/auth/me`）与 `permissions` 判权、运行时开关的注册页、权限驱动的租户管理页，以及 `E2E_REAL_BACKEND=1` 门控的真机用例。

- `unwrap` 的签名与行为未变，既有 5 条用例保持不动。
- 契约中的 `/api/v1/admin/error-codes` 与 `/api/v1/admin/ratelimit/auth` 地址已修正，但 console 能力还没有接上认证链，运行时仍返回 401；前端不消费这两个端点。

## 平台用户管理与双工作台

### 新增

- `/hub` 工作台选择入口和 `src/features/hub/views/HubView.vue`：零角色用户直接进入 `/workspace`；可访问管理面的用户首次进入时选择「用户工作区」或「管理控制台」，选择结果写入 `jimu.last_surface`，后续进入 `/hub` 恢复最近可用工作台。
- `src/shared/auth/surfaces.ts`：`AppSurface`、`canAccessWorkspace()`、`canAccessAdminSurface()`、`readLastSurface()`、`rememberSurface()`。管理面可用性只由 `GET /api/v1/users` 或 `GET /api/v1/tenants` 决定，不从角色名推断。
- `src/layouts/UserLayout.vue` 与拆分后的路由树：`/workspace`、`/workspace/account/security` 使用用户工作区布局；`/admin`、`/admin/users`、`/admin/tenants`、`/admin/account/security` 使用管理控制台布局。`/admin/*` 带 `requiresAdmin` 守卫，身份成功加载但无管理面读取权限时回到 `/workspace`。
- 兼容重定向：`/portal` → `/hub`、`/platform/tenants` → `/admin/tenants`、`/account/security` → `/workspace/account/security`；登录默认入口改为 `/hub`，明确深链接仍优先。
- `src/features/users/params.ts`、`src/features/users/api.ts`：用户列表查询、详情、创建、更新、停用、角色替换、按租户加载角色和租户选项。用户、租户、角色 ID 全部按字符串处理；停用接口接受 `204` 空响应。
- `src/features/users/views/UsersView.vue`：用户名/租户/状态筛选、分页表格、创建抽屉、编辑抽屉、角色分配对话框和停用确认。创建用户必须选择所属租户；切换租户会清空角色选择；角色读取权限缺失时不显示角色操作。
- `tests/unit/surfaces.spec.ts`、`hub-view.spec.ts`、`router.spec.ts`、`user-params.spec.ts`、`users-api.spec.ts`、`users-view.spec.ts`，以及 `e2e/workspaces.spec.ts`、`e2e/users.spec.ts`。

### 变更

- 契约 pin 更新为 `cf116508ba73763edcf97599a9436628ce3969b1`，同步 `application.UserResponse`、`UserPageResponse`、`RoleResponse`、`AssignUserRolesRequest` 等 DTO。租户、用户、角色 ID 及相关路径参数改为 string，租户页移除 `isPreciseId` 守卫和不可精确 ID 提示。
- `PortalLayout.vue` 的导航改为管理控制台语义，增加权限驱动的「用户管理」；账户菜单提供账号安全、切换用户工作区和退出登录，不再展示角色文案或顶部用户信息。
- `PortalView.vue` 的租户管理与账号安全链接迁移到 `/admin/*`；`e2e/helpers/session.ts` 的平台管理员权限同步包含用户、角色和租户管理能力。
- `e2e/real-backend.spec.ts` 删除 P1 的 `test.fixme`，重新启用「新建租户 → 分配套餐 → 删除」真实链路，并更新双工作台路由与字符串 ID 断言。

### 修复

- 后端把雪花 ID 改为字符串后，前端不再把 ID 转回 `number`；API 请求、路由路径、表格 key 和角色载荷均原样保留字符串 ID。
- 管理面不再只靠登录成功放行：只有服务端 `permissions` 提供用户或租户读取能力时才进入 `/admin`；具体行内动作继续按各自资源与动作判权。
- 用户「删除」在界面统一表述为「停用」，确认文案明确账号数据保留且可通过编辑重新启用，避免把软删除误导为不可恢复的删除。
- 会话清理会通过 `onSessionCleared` 同步清空 TanStack Query 缓存，避免在同一 SPA 会话中切换账号后短暂展示上一个管理员缓存的跨租户数据。
- 只有用户管理权限、没有租户列表读取权限的租户管理员现在可以创建用户：创建面板隐藏租户选择并省略 `tenant_id`，角色请求也不再强制带租户参数，由后端依据当前身份解析归属。
- 深链接和账户菜单的工作台切换会在路由守卫中写入最近工作台，`/hub` 不再只恢复通过选择卡片进入的工作台。
- `/hub` 遇到身份加载暂时不可用时保留页面并显示可重试错误态，不再把「无法确认权限」误判成「没有管理权限」而直接送到用户工作区。
- 租户和角色选项改为读取全部分页；超过 100 个租户或角色时不会静默丢弃后续条目。

### 验证

- `pnpm run check` 通过：`api:check`、Prettier、ESLint、`vue-tsc`、Vitest 与生产构建全部通过；单测 **219 条 / 26 个文件**全绿。ESLint 仅保留既有 `e2e/real-backend.spec.ts` 的 `playwright/no-skipped-test` warning，0 error。
- `pnpm run test:e2e` 通过：**25 passed / 2 skipped**。跳过的是 `E2E_REAL_BACKEND=1` 门控的两条真机用例；本轮默认套件完整覆盖 `/hub` 分流、最近工作台恢复、越权回退、旧路由、用户列表、创建、编辑、角色替换和停用。
- TDD 证据：契约同步后先由 `vue-tsc` 报出租户 API 仍使用 number；字符串 ID 用例先失败在旧 `isPreciseId` 守卫；工作台与路由用例先失败在缺失 `HubView` 和旧 `/portal` 默认入口；用户 API/页面用例先失败在模块不存在与交互缺失，再逐项转绿。

### 说明

- 管理面权限条件只用于决定是否显示工作台入口；页面内列表和每个写操作仍分别检查自己的请求路径，不能用一个页面级权限替代行内判权。
- 平台管理员创建用户时选择 `tenant_id`，这是唯一由平台主动指定目标租户的请求字段；普通页面请求不从 header、query 或缓存推导租户上下文。
- 角色列表使用 `GET /api/v1/roles?tenant_id=...` 按目标租户加载，创建与角色替换都由后端做最终归属校验。
- 用户管理首版不包含批量停用、导入导出、邀请注册、密码重置或跨租户迁移。

## 管理页统一模板

### 新增

- `src/shared/components/ManagementPage.vue`：管理台列表页共用的页头、筛选卡片、加载/错误/空/无权限状态、表格表面与分页容器。组件通过 `filters`、`table`、`empty-action`、`dialogs` 插槽保留各能力的业务内容，不复制列表页视觉规则。
- `tests/unit/management-page.spec.ts`：锁定共享页头、筛选、表格、弹层、分页事件和五种互斥状态的契约。

### 变更

- `src/features/users/views/UsersView.vue` 与 `src/features/tenants/views/TenantsView.vue` 改为复用同一管理页骨架。两页的标题层级、说明文字、筛选卡片边框与内边距、状态间距、表格表面和分页间距现在来自同一份实现。
- 租户页筛选从裸 flex 容器改为带可见标签的 `el-form`，与用户页统一使用“标签 + 控件”的密度和间距；搜索、新建操作统一放在筛选栏右侧。
- 两页的新建与编辑都使用 480px 右侧 `el-drawer`；分配角色与分配套餐继续使用轻量 `el-dialog`，交互容器按任务复杂度保持一致。
- Element Plus 的状态标签、表格和分页继续由原生组件承担，项目层只补充 Carbon token 对应的表面、边框和间距，不新增页面级动画。

- `pnpm run test:e2e` 通过：**25 passed / 2 skipped**，跳过项仍为 `E2E_REAL_BACKEND=1` 门控的真机用例。
