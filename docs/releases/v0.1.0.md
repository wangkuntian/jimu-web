# v0.1.0

## 亮点

- 首版 Jimu Portal 前端：Vue 3 + TypeScript + Vite 的独立 SPA，与后端 `jimu` 通过版本化 OpenAPI 契约关联，不复制后端领域规则，两个仓库独立版本化与发布。
- 一次把工程门禁与协作流程立起来：本地 `pnpm run check` 与 CI 的分领域 job 等价，提交消息、版本日志、依赖更新都有强制或自动化入口，分支保护只 required 一个稳定的聚合检查 `CI Gate`。

## 新增

- 应用壳：`/` 重定向到 `/portal`，`/portal`、`/workspace`、`/account/security` 三个静态页面，Pinia 会话 store 只定义前端状态边界。
- 契约链路：`contracts/jimu.swagger.yaml`（Swagger 2.0 固定副本）、`contracts/jimu.openapi.yaml`、`contracts/backend-commit.txt`（来源提交 `3dea4ab`）、`src/shared/api/generated.ts` 类型派生。
- 工程工具：pnpm 11.23.0、Prettier、ESLint、vue-tsc、Vitest、Vue Test Utils、Playwright、openapi-typescript、swagger2openapi。
- CI：`Changes` 路由 + `Policy` / `Quality & Tests (node 22/24)` / `API Contract` / `Build` / `E2E (Playwright)` 分领域 job + 聚合门禁 `CI Gate`；纯文档 PR 只跑策略层。
- 发布：`.github/workflows/release.yml` 由 tag 触发，校验 tag 指向当前 `master` tip 后构建并发布静态资源包 `jimu-portal-<tag>.tar.gz`，Release body 取自 `docs/releases/<tag>.md`。
- 流程规范：[`docs/CONTRIBUTING.md`](../CONTRIBUTING.md)、PR 与 issue 模板、`githooks/commit-msg` 提交消息门禁（本地钩子与 CI 共用一份实现）、dependabot 依赖更新。

## 验证

- `pnpm run check`：契约同步、格式、lint、类型、单测与构建全部通过（本地 Node 24 / pnpm 11.23.0）。
- Playwright E2E：CI run `38036749455` 中 `pnpm run test:e2e` 通过（chromium）。
- 发布前需确认本版本的 PR 已通过 `CI Gate`，且 tag 打在 `master` tip 上。

## 说明

- 开发环境要求 Node.js `>=22.13.0`：pnpm 11.23.0 自身要求 Node ≥22.13（依赖 `node:sqlite`），首版曾按 `^20.19.0` 声明并在 CI 里试跑 Node 20，实测在 setup 阶段即失败，已据此收紧 `engines` 与 CI 矩阵。
- 当前只有静态壳，尚未接入后端认证与任何业务域；登录、会话刷新、租户范围与无权限访问的测试待对应功能实现时补充。
- 后端 Swagger 源的 `/api/v1/admin/error-codes` 与 `/api/v1/admin/ratelimit/auth` 已含 `basePath` 前缀，转换后存在重复 `/api/v1` 的风险，暂不可依赖这两个生成路径，待后端修复后重新同步契约。
- 契约固定提交 `3dea4ab` 目前只在后端仓库的对象可达范围内，不在其后端 `master` 历史中；后端把契约同步回 `master` 后应重新运行 `pnpm run api:types` 刷新该提交。
- 尚未确定静态托管目标；发布产物为通用静态包，部署方式在首个真实环境确定后补充。
